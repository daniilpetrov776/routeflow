# RouteFlow

Приложение для построения маршрутов с использованием Yandex Maps API.

## Структура проекта

Проект разделен на два отдельных приложения:

- **`client/`** - React клиентское приложение
- **`server/`** - Express серверное приложение
- **`shared/`** - Общие типы и схемы

## Быстрый старт

### 1. Запуск сервера

```bash
cd server
npm install
cp env.example .env
# Отредактируйте .env файл
npm run dev
```

Сервер будет доступен на http://localhost:5001

### 2. Запуск клиента

```bash
cd client
npm install
cp env.example .env.local
# Отредактируйте .env.local файл
npm run dev
```

Клиент будет доступен на http://localhost:3000

## Развертывание

### Сервер

```bash
cd server
npm run build
npm start
```

### Клиент

```bash
cd client
npm run build
# Разверните папку dist на ваш хостинг
```

## Переменные окружения

### Сервер (.env)
- `PORT` - Порт сервера (по умолчанию 5001)
- `DATABASE_URL` - URL базы данных
- `SESSION_SECRET` - Секрет для сессий
- `CLIENT_URL` - URL клиентского приложения
- `NODE_ENV` - Окружение (development/production)
- `YANDEX_MAPS_API_KEY` - API ключ Yandex Maps (обязательно)
- `ALLOWED_ORIGINS` - Разрешенные источники для CORS (через запятую)

### Клиент (.env.local)
- `VITE_API_URL` - URL API сервера
- **Примечание**: API ключ Yandex Maps больше не используется на клиенте. Все запросы проксируются через сервер.

## Технологии

- **Клиент**: React, TypeScript, Vite, Tailwind CSS, Redux Toolkit, React Query, DOMPurify, toast, retry logic
- **Сервер**: Node.js, Express, TypeScript, Drizzle ORM, Winston, express-rate-limit
- **Общее**: Zod для валидации

## 🔴 Критические проблемы

### 1. Отсутствие валидации переменных окружения

**Проблема**: Переменные окружения используются без валидации при старте приложения.

**Местоположение**: 
- `server/index.ts` - использование `process.env` без проверки
- `server/lib/api-keys.ts` - ключ API проверяется только при использовании

**Риски**:
- Приложение может запуститься с неполными настройками
- Ошибки обнаруживаются только во время выполнения запросов
- Проблемы с конфигурацией в production

**Рекомендация**:
```typescript
// Создать server/lib/env.ts
import { z } from 'zod';

const envSchema = z.object({
  NODE_ENV: z.enum(['development', 'production', 'test']).default('development'),
  PORT: z.string().transform(Number).pipe(z.number().min(1).max(65535)).default('5001'),
  YANDEX_MAPS_API_KEY: z.string().min(1, 'Yandex Maps API key is required'),
  CLIENT_URL: z.string().url().optional(),
  ALLOWED_ORIGINS: z.string().optional(),
  DATABASE_URL: z.string().url().optional(),
  SESSION_SECRET: z.string().min(32).optional(),
});

export const env = envSchema.parse(process.env);
```

### 2. Небезопасное хранение паролей

**Проблема**: В схеме базы данных пароли хранятся в открытом виде (`text`).

**Местоположение**: `shared/schema.ts`, `server/shared/schema.ts`

**Риски**:
- При компрометации БД все пароли будут доступны
- Нарушение базовых принципов безопасности

**Рекомендация**:
- Использовать хеширование паролей (bcrypt, argon2)
- Добавить валидацию сложности паролей
- Реализовать сброс пароля через email

## 🟡 Важные проблемы

### 3. Использование типа `any` в критических местах ✅ ИСПРАВЛЕНО

**Проблема**: Тип `any` используется в роутах и обработчиках ошибок, что снижает безопасность типов.

**Местоположение**:
- `server/routes/*.ts` - параметр `app: any`
- `server/index.ts` - `err: any` в error handler
- `client/src/hooks/useRouteCalculation.ts` - `routeParams: any`, `event: any`

**Исправлено**:
- ✅ Все `app: any` заменены на `app: Express` в роутах
- ✅ `err: any` заменен на `err: Error & { status?: number; statusCode?: number }` в error handler
- ✅ `routeParams: any` заменен на `routeParams: RoutingParams`
- ✅ `event: any` заменен на `event?: YandexEvent` с добавлением типа `YandexEvent` в типы Yandex Maps
- ✅ `item: any` в suggest.ts заменен на `YandexGeocoderFeatureMember`
- ✅ Улучшена типизация в `requestLogger.ts` (заменен `any` на `unknown` где возможно)

### 4. Отсутствие аутентификации и авторизации

**Проблема**: В проекте есть зависимости для аутентификации (passport, express-session), но они не используются.

**Риски**:
- Нет защиты API от неавторизованного доступа
- Нет разграничения доступа к данным пользователей
- `getUserRoutes` возвращает все маршруты, а не только пользователя

**Рекомендация**:
- Реализовать middleware для проверки аутентификации
- Добавить проверку прав доступа к маршрутам
- Использовать JWT токены или сессии

### 5. Проблемы с CORS конфигурацией

**Проблема**: В production режиме, если `ALLOWED_ORIGINS` не задан, используется fallback `https://your-client-domain.com`.

**Местоположение**: `server/index.ts:21`

**Риски**:
- Неправильная конфигурация может привести к блокировке легитимных запросов
- Fallback значение не является реальным доменом

**Рекомендация**:
- Выбрасывать ошибку при отсутствии `CLIENT_URL` или `ALLOWED_ORIGINS` в production
- Добавить валидацию URL при старте

### 6. Отсутствие тестов

**Проблема**: В проекте нет тестов (unit, integration, e2e).

**Риски**:
- Невозможно гарантировать работоспособность после изменений
- Высокий риск регрессий
- Сложность рефакторинга

**Рекомендация**:
- Добавить Jest/Vitest для unit тестов
- Написать тесты для валидации схем
- Добавить интеграционные тесты для API
- Использовать Playwright для e2e тестов

### 7. Проблемы с обработкой ошибок в клиенте

**Проблема**: В `queryClient.ts` есть хардкод URL для production.

**Местоположение**: `client/src/lib/queryClient.ts:8`

**Риски**:
- Неправильная конфигурация приведет к ошибкам в production
- Сложность деплоя на разные окружения

**Рекомендация**:
- Убрать хардкод, использовать только `VITE_API_URL`
- Добавить валидацию переменных окружения на клиенте
